# U-Boot 基础层细化讨论

本文用来逐项决定实现前的接口、布局与更新规则。范围已锁定为当前 i.MX6ULL 板卡、MBR/ext4、外部描述和带 target hash 门控的产品 U-Boot 更新；不再讨论是否把 BusyBox/BR 固化进核心。需求与判据见 [issue.md](issue.md)。下列建议不是用户已确认方案，也不是现有可执行接口。

## D1 · ext4 分区组织：首先讨论

必须同时满足“独立更新 rtfs Sparse”和“保留 kernel/DTB”。MBR/ext4 已确认，但 ext4 分区数量没有确认。

| 候选 | 行为与代价 |
|---|---|
| 独立 ext4 启动区＋ext4 rtfs 区 | kernel/DTB/启动配置位于启动区；rtfs Sparse 可直接替换另一区域。天然符合组件隔离，但需要两个 ext4 区域。分区编号、起点和容量由外部描述决定，不固定 p1/p2。 |
| 单一 ext4，kernel/DTB 与 rtfs 共存 | kernel/DTB 文件可单独更新；直接用 rtfs Sparse 覆盖整个分区会连它们一起替换。要保持旧 kernel/DTB，需要另行定义保存、合并和元数据处理，不能把整分区写说成仅替换 rtfs。 |

**建议先选择两个独立 ext4 区域**，但不将这个建议写成默认实现。待决定：区域是否分离、MBR 启动标志的用法、分区角色与组件位置的描述方式。此前 FAT32＋固定 128 MiB/2 GiB 不作为新方案输入。

## D2 · 外部布局／启动描述的最小内容

“一份 Sparse＋外部描述”已确认。描述文件格式与字段还没有确认，不直接把旧 layout.json 当成契约。

| 信息 | 应表达的内容 |
|---|---|
| 板卡／介质 | 当前板卡身份、存储设备选择、user area 与 bootloader 硬件区域的区分；不扩展其他板卡。 |
| MBR | 分区标识、起点、容量、类型、启动角色与合法对齐。是否支持扩展／逻辑分区须明确，不能泛称支持全部 MBR 变体。 |
| 组件定位 | kernel、DTB、启动配置所属区域和最终路径；rtfs 所属区域。输入文件 basename 不决定最终路径。 |
| 启动 | 启动配置格式、定位规则、入口选择；kernel/DTB 路径和 root 参数由项目提供。 |
| 固件目标 | 产品 U-Boot 的介质区域、偏移、容量及 hash 比较规则，与整盘 user area 的地址空间分开。 |
| 检查 | 版本／单位、必需字段、范围重叠、容量超限、描述与实际 MBR／启动配置矛盾时的拒绝规则。 |

建议使用一种带版本的机器可读格式，例如 JSON；具体 schema 需讨论后固定。主机 source/toolchain/work/input/output/log 路径属于调用参数，不应被布局描述绑到某个仓库绝对路径。

## D3 · 通用固件怎样定位启动配置

“不能编译项目文件名和 root 参数”不等于“不能识别标准启动协议”。应区分标准协议发现约定与项目配置。

候选方案是按 MBR 的启动角色选择 ext4 区域，再读取标准 extlinux 配置；配置内的 kernel/DTB 路径及 bootargs 由项目决定。是否保留默认发现位置、是否允许描述指定其他位置、多入口如何选择，均待决定。布局描述与 extlinux 若重复表达组件位置，必须核对一致性，不能静默采用其中之一。

ROM 下载路径只负责初始化后进入下载服务，不依赖 Linux 是否可启动。普通 eMMC 路径依配置启动，失败时保留可诊断状态；恢复策略、启动延时与交互窗口也要明确，而不是沿用旧脚本的隐含行为。

## D4 · ext4 文件更新的真实能力

kernel/DTB 独立更新不能继续使用 FAT 操作。下一阶段需核对固定 U-Boot 源码的 ext4 写支持、目录操作、截断、空间检查和错误返回；源码能力不清楚前不承诺已经可用。

待固定：支持的 ext4 特性集合、是否要求干净文件系统、日志／元数据校验方式、比旧文件更大或更小时的行为，以及目标目录不存在时是拒绝还是允许显式创建。空间不足和元数据不支持必须在写前尽量拒绝，不能边修改目标边试探。

主机修改镜像与板端更新应使用一致的组件定位规则，但不必使用同一个文件系统实现。保留判据需区分“未选文件内容保持不变”和“允许修改必要 ext4 元数据”；不能要求文件更新后整个文件系统逐字节不变。

## D5 · 整盘 Sparse、独立 rtfs Sparse 与局部替换

Sparse 块记录相对于操作目标，不自行携带组件名称。整盘输入相对于 user area；独立 rtfs 输入相对于描述指定的 rtfs 区域。两者不能互相误当成 raw 或重复包装。

待固定：接受的 Sparse 版本与块大小、rtfs 展开长度要求等于区域容量还是允许小于容量、区域尾部处理、校验块的支持与结果，以及对 ext4 已分配块误跳过的检测方式。不能因为旧实现要求 2 GiB，就继续强迫所有输入同样大小。

已有 Sparse 的 replace 默认生成新文件，原文件不变。kernel/DTB 替换只改指定文件和必要元数据；rtfs 替换只改指定区域。MBR、其他组件、启动配置以及未选范围的 RAW/FILL/DONT_CARE 语义保持不变。改变布局或启动参数不属于隐含局部替换，需要另一项明确请求。

纯合成／替换不依赖固件；直接板卡组件更新不依赖完整镜像或其他组件输入。是否额外支持从整盘 Sparse 取出指定组件再写板，可作为便利接口讨论，不能取代这两条独立路径。

## D6 · 产品 U-Boot 的 hash 比较范围

用户要求目标一致时跳过产品 U-Boot 擦写，不是“每次都写后再校验”。

需要先决定比较对象：本板产品固件的有效字节、目标偏移、输入长度、扇区对齐和尾部填充。不能拿任意 1 MiB 保留区的 hash 与较短的 .imx 文件 hash 比较。IVT/DCD、boot0 偏移等来自本板实际 ROM 启动条件，不来自 BusyBox/BR 项目。

| 镜像比较 | 启动设置 | 部署判定 |
|---|---|---|
| 相同 | 正确 | 跳过产品镜像擦写；记录本轮 target hash 与 skipped 结果。启动设置是否也免重复写，需固定检查规则。 |
| 相同 | 错误 | 仍跳过产品镜像擦写，但不能宣称已可正常启动；处理必要启动设置并记录。 |
| 不同 | 任意 | 更新产品镜像，重新读回比较，再检查／处理启动设置。 |
| 读取失败／范围不明 | 任意 | 停止，不把错误当成不同而自动覆盖。 |

hash 判断放在主机还是板端、怎样把比较结果可靠交给 UUU 流程，须按固定版本能力决定。外部必须观察到比较范围、hash、写入／跳过分支、读回结果；只有 host 的 skipped 提示不够。整盘系统写入仍按 Sparse 映射执行，本轮没有确认对全部组件做自动差分更新。

## D7 · 操作接口与路径

接口需要表达如下操作，但名称、参数及 CLI 形态尚未定稿；下表不是可执行命令。

| 操作 | 必需输入 | 不得额外强制要求 |
|---|---|---|
| 固件构建 | U-Boot 源码身份、工具链、构建输出与板级输入 | 某项目 kernel/rtfs 或固定仓库 CWD |
| 整盘合成 | 布局、启动配置、kernel、DTB、rtfs Sparse、输出 | 固件或完整项目包 |
| 已有镜像替换 | 已有 Sparse、描述、指定新组件、新输出 | 所有组件重新生成 |
| 整盘部署 | loader／产品固件、整盘 Sparse、描述、目标选择 | BusyBox/BR 版本、归档或项目工作区 |
| 独立组件部署 | loader、指定组件、描述、目标选择 | 完整系统包和未选组件 |
| 独立产品固件部署 | loader／产品固件、固件目标、目标选择 | 系统 Sparse、kernel/DTB/rtfs |

loader 与产品镜像可同文件但角色应明确。整盘部署包含产品 U-Boot 的 hash 门控更新；独立组件部署保留 bootloader。各入口均需一致的主机预检、正式确认、日志和失败语义。

默认路径可以是示例或便利值，不可成为接口硬条件。最终文档应使用同一组 source/work/firmware/image/layout/input/output/log 角色，明确每一步消费哪一种，而不是在 out 与 build 之间隐式切换。

## D8 · 验证与迁移顺序

建议按 D1→D2/D3→D4/D5→D6/D7 的顺序讨论，确认后才写实施路线。未完成前，不把旧 FAT32 或 BusyBox 专用脚本修补成“通用”结论。

主机验证覆盖可变文件名／路径、不同合法布局、无完整包的独立输入、已有镜像局部替换、ext4 兼容性、范围越界及 Sparse 零值／跳过规则。板级验证覆盖 ROM、下载服务、ext4 文件更新、整盘及组件冷启动，以及产品 hash 的相同／不同／失败分支。

03 BusyBox 作为外部实例提供自己的布局和启动配置，不能修改核心默认值来迁就它。产品 hash 的不同分支应使用两个合法构建镜像，不为测试主动破坏目标 bootloader。实板写操作仍由开发者确认执行。
