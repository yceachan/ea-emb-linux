B

· 固件启动与可复现输入

入口：firmware/build.sh、firmware/base-revision、firmware/register-board.patch、firmware/overlay/。

build.sh 从固定 U-Boot revision 导出源码，再应用 overlay 和补丁。UBOOT_SOURCE、CROSS_COMPILE 和构建目录由外部提供。它记录源码树、板级输入及配置摘要，后续构建发现输入变化就要求重新 configure。这个方式符合路径独立和输入可追溯的需求；完整 SDK 构建应由开发者执行，默认 -j12。

overlay/board/100ask/imx6ull/imx6ull.c::board_late_init() 用 is_boot_from_usb() 区分启动来源。ROM USB 路径将 RAM 环境中的 bootdelay 设为 0，bootcmd 设为 fastboot usb 0；eMMC 路径保留默认启动行为。100ask_imx6ull_defconfig 配置 3 秒等待、ENV_IS_NOWHERE、MMC／fastboot、CMD_EXT4_WRITE 和 CMD_SYSBOOT。

overlay/include/configs/100ask_imx6ull.h 中的 uuf_scan 扫描活动分区中的 /extlinux/extlinux.conf，通过 sysboot 启动。启动项内容由文件维护，不要求修改持久化 U-Boot 环境。它使用 sysboot 实现 extlinux 引导，配置中没有启用 BOOTSTD。

迁入时保留 02 的 DDR、UART、USB、eMMC 基线与固定 revision。USB 自动 fastboot、eMMC 3 秒打断及冷启动仍需实板验收。现有扫描按顺序尝试启动，不能作为主机“多个目标候选时明确选择”的实现。网络启动扩展按 issue 后续安排处理。

package.py::validate_firmware()、imx() 可参考其构建清单、关键配置、IVT／DCD／Boot Data 和 boot0 容量检查。板级参数属于当前板卡；旧代码中的 0xffc00 上限须与实际镜像及 boot0 容量共同核对。

C

· 原始文件的定向覆盖

入口：firmware/overlay/board/100ask/imx6ull/uuf.c::file_target()、file_write()、hash_file()，以及 firmware/ext4-io.patch。

主机验证原始 zImage 或 DTB，下载到 fastboot buffer；板端检查下载长度与 SHA-256，先确认目标文件可写，再调用 fs_write() 覆盖。写后按文件长度与 hash 读回核验。主机源文件名和板端目标路径分别传递，符合独立更新保留其他文件的需求。

这条路线依赖真实 U-Boot ext4 写入能力。补丁包含以下有依据的修正：

  • ext4fs_io_error 记录一次挂载操作中的 I/O 故障；短读、短写传递到调用者，后续写入停止。
  • put_ext4() 检查分区边界，对非整扇区写入先读后改，保留相邻字节。
  • 完整读取父 inode，保留父目录扩展字段；覆盖已有文件时保留 mode、UID／GID 及高位身份字段。
  • ext4fs_deinit() 返回清理错误。journal 清理失败时保留磁盘 RECOVER 标志，不能报告成功。
  • ext4fs_free_journal() 处理部分分配状态并清空指针。

ext4fs_file_writable() 是这版 unlink／create 写入器的能力门控：只接受已有普通单链接文件，拒绝符号链接、硬链接、目标 xattr／ACL 和不支持的 inode flags。它不提供原子替换或断电回滚；发生故障后只能停止，并保留故障状态供恢复处理。

package.py::superblock(writable=True) 与 make_ext4() 配合控制 kernel ext4 特性：4096 字节块、journal、明确的特性集合和干净状态。制像关闭 metadata_csum、64bit、orphan_file、dir_index、flex_bg，并避免把主机 xattr 复制到 kernel 文件。预检仍需检查真实文件系统和目标 inode，不能仅依赖主机制像配置。

下载缓冲区和 heap 都是 16 MiB。真实输入应检查大小、RAM 地址及写入器内存占用。遇到支持范围之外的输入时，按 issue 对齐替代路线；本参考不把整 kernel 分区重写作为文件更新方案。

D

· Sparse 制像与有效范围核验

入口：uuflib/images.py::ext4_allocated()、encode_sparse()、Sparse，uuflib/package.py::validate_sparse()。

ext4_allocated() 先运行只读 e2fsck，再用 dumpe2fs 的空闲块清单求出已分配块。encode_sparse() 只把空闲块编码为 DONT_CARE；已分配块使用 RAW，重复的 4 字节模式可编码为 FILL。已分配的全零块同样写入，不能按“内容为零”判断是否跳过。

Sparse 检查 header、chunk 长度、逻辑容量和尾部数据。validate_sparse() 展开主机文件，核对 ext4 容量、状态和分配范围，拒绝跳过元数据或已分配内容的镜像。原语中的格式范围是 4096 字节块、RAW／FILL／DONT_CARE，不能把它描述成支持所有 Sparse 格式变体。

Sparse.checks(lba_base) 为 RAW／FILL 生成不超过 4 MiB 的读回 hash 范围。backend.py::Session.write_lines() 用 fastboot raw partition 描述目标起点和长度，再调用 UUU flash。板端 hash_range() 用 1 MiB 窗口读取介质，返回范围 hash。

迁入时从最终 MBR 获取分区容量，核对 blk_sz × total_blks。计划应分别表达容器字节数、分区容量和有效写入范围。旧 Session.plan() 在合并文件记录时覆盖了分区 bytes，这段计划代码必须改写。

DONT_CARE 可保留旧介质内容，核验应覆盖有效写入块。逻辑重建由两个新 ext4 实现，不能把展开补零后的整分区 hash 或物理 erase 加为布局更新的条件。

E

· 归档、MBR 与启动描述

入口：uuflib/package.py::make_ext4()、pack()、archive()、unpack()、verify_sums()，uuflib/model.py::mbr()、parse_mbr()、boot_text()、parse_boot()。

归档原语已具备普通文件／目录约束、相对路径检查、重复成员检查和 SHA-256 核验。archive() 归一化 tar 的所有者与时间；unpack() 在提取前检查成员，再校验清单。Session.stage() 将输入复制到任务目录并复核 hash，后续执行使用暂存文件，避免输入在计划后变化。

pack() 可借鉴“准备 kernel 文件树→制 ext4→编码两张 Sparse→检查→生成清单”的步骤。旧代码只重建 kernel ext4，rtfs 由外部提供；它没有实现当前布局更新时重建两个 ext4 的规则。

旧归档带 profile.json，主机从该对象生成并比较 MBR，同时混入固件目标和启动配置。迁入时必须按当前 ADR 改写数据来源：

对象 迁入后的职责
最终 MBR 分区起点、长度、类型、活动标志、disk signature 的唯一来源
归档清单 载荷到 MBR 表项的明确映射、文件校验；不再复制几何
固件部署描述 boot0 范围、boot ack、启动区域；与 user area 布局分开
启动描述 kernel／DTB 文件目标、启动项及 rtfs 引用；与几何编辑分开
制像输入 载荷与预留量；结果写入最终 MBR，并制作匹配的两个 ext4

mbr() 的字段编码可作参考，但其几何来源是旧 profile。parse_mbr() 只接受两个 Linux 主分区，不能用于拒绝空盘的基础探测。应保留原始 MBR 状态，待具体操作需要时再校验产品布局。活动标志和分区类型也不能单独确定 kernel／rtfs 角色。

parse_boot() 支持明确 label、DEFAULT 或唯一启动项，拒绝重复与缺失字段；适合参考其消歧方式。旧 schema 强制 APPEND 与 profile 一致、把启动配置修改耦合到分区镜像，这部分需按当前启动配置独立维护的要求改写。

旧 deploy --bundle 仅接收解包目录。下一次实现须在共用后端中接收归档文件，内部调用安全解包与校验，然后生成同一计划；保留独立解包入口。现有函数不能证明“直接选归档部署”已经实现。

旧 cli.py::make_profile() 接受 rootfs 树或 ext4／Sparse，但固定了 128 MiB kernel 容量。可借鉴输入识别，默认几何须按实际载荷与预留量计算。busybox() 的 fakeroot 制像及 /boot 挂载准备可用于首轮 03 载荷；其 rcS 字符串替换依赖 03 基线，Linux MMC 编号仍需实测。

F

· 共享后端、设备复核与写入保护

入口：uuflib/cli.py::dispatch()、rpc_arguments()、confirm_terminal()、confirm_rpc()，uuflib/backend.py::Session，uuflib/transport.py，板端 uuf.c。

CLI 和 GUI 经同一参数解析、dispatcher 与 Session 执行。GUI 使用 JSON Lines 事件接收计划、目标、确认、日志和结果，确认回复带随机 token。这种共用方式可保留；旧 profile 与 plan 的字段结构需先按当前 ADR 重构。

Session.execute() 的可借鉴顺序为：主机预检和 UUU 离线解析→确认 RAM loader 下载→枚举并选择 ROM USB 设备→读取真实设备→形成实际计划并确认→再次探测→写入和核验。--dry-run 在主机预检后返回，避免进入 USB 枚举与下载路径。

probe(boot=False) 已能读取 CID、user／boot0 容量、擦除粒度、EXT_CSD 和原始 MBR；export_data() 经 getvar 分段传送小块只读数据。可从这里建立基础探测。旧 execute() 却让 inspect 总是进入 probe(boot=True)，强制要求产品 MBR 和 extlinux；应改为先返回基础信息，再按操作需要定位文件。

写入前 matchcid 与旧 MBR hash 复核用于绑定确认对象；写后再次检查 CID、EXT_CSD 和最终布局。布局更新核对确认时的旧状态即可，不能要求新旧 MBR 相同。独立组件更新则核对实际布局和明确目标映射。

uuf.c::firmware() 检查 boot0、偏移、容量、下载长度和 hash。目标 hash 相同时跳过写入；不同则分段写入，对末扇区未使用字节先读后保留，逐段和最终读回核验。bootconf() 独立检查和设置 EXT_CSD，因此固件内容相同也能修正启动设置。

uuf.c::erase() 根据真实 erase group 拒绝不对齐范围，不扩大目标，并按设备声明的擦除值读回。主机旧擦除计划只比较分区编号和几何，未可靠绑定角色。必须用当前明确映射复核目标；交换 kernel／rtfs 名称及其几何后仍通过的旧逻辑不可迁入。

save／filesave／keep 保存写前 hash，再比较未选组件、分区外范围和 Sparse 跳过块。它们保存的是摘要，不能恢复数据。旧主机实现会扫描大量未写范围，且有 2048 槽上限；可借鉴保护方法，按实际计划和验收目标评估范围与耗时，不把整介质扫描固定为新要求。

transport.run() 用 PTY 持续消费 UUU 输出，设置总时限并写日志；complete() 同时检查退出状态、错误输出及每条命令成功记录。匹配规则来自旧 UUU 输出，迁入时应核对实际 UUU 版本。stop() 对 UUU 进程组执行 TERM、超时后 KILL 并 wait，但重复取消能中断等待；需先完成可靠清理，再向 GUI 报告停止。

G

· GUI 可保留的交互基础

入口：gui/src-tauri/src/main.rs、gui/src/main.tsx、gui/src-tauri/tauri.conf.json。

Tauri 负责原生路径选择、启动 Python 后端、转发事件和确认输入。Backend(Mutex<Option<Running>>) 限制同一窗口只运行一个任务。运行时按可执行文件相邻的 backend/uuf 定位后端；开发时使用源码路径。发布需要一起提供后端和固件输入，并明确主机工具依赖。

pick_path() 区分目录、打开文件和保存文件。React 的选择逻辑为新输出目录选择父目录后生成新路径，rootfs 输入同时支持目录与镜像。事件监听建立后才开放执行按钮，运行时禁止修改输入。窗口按显示器逻辑宽高各一半设置并居中，符合约四分之一面积的要求。

可保留实际分区、待写范围、镜像信息和日志的展示能力。页面改为 issue 要求的“烧录／镜像准备／设备信息”，采用米白底与橙棕强调；布局编辑操作最终 MBR，镜像准备保留制像、打包与解包。

组件选择须由后端实际计划落实。旧 bundle 路径强制部署 U-Boot，而界面允许取消勾选；应按当前任务规则修正选择与计划的一致性。取消按钮及确认对话框的取消需共享清理状态，等待 Python 与 UUU 都退出后才恢复可操作状态。旧界面和取消实现不能直接作为验收基线。

· 下一次运行的使用顺序

先读取当前 issue 与 ADR，再查本文的实现入口。按 route.md 实施时，优先迁入与数据模型无关的固件、ext4 和 Sparse 原语；归档、定位、计划和 GUI 在新职责下重做连接。逐文件迁入前检查依赖，避免整体恢复三个失败实现提交。

主机、固件构建、GUI 交互和实板证据分别报告状态。完整构建命令交给开发者把关；硬件写操作与冷启动由开发者验收。当前 issue 仍处于待实现状态。
