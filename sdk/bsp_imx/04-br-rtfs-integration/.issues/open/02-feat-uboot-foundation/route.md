# 实施路线

2026-10-12：当前交付为需求与技术路线对齐，源码迁移和实现尚未完成。行为与验收见 [issue.md](issue.md)，技术约束见 [adr.md](adr.md)。

## R1 · 固定输入与固件能力

在隔离 worktree 中建立 `uuf/` 产品源码，迁入 02 的固定 U-Boot 板级输入和构建入口。补齐 ROM USB 自动 fastboot、boot0 产品启动、extlinux 发现、3 秒控制台打断和 ext4 文件写入。

先完成配置与轻量编译检查，再交付完整构建命令给开发者执行，默认 `-j12`。使用 03 的真实 kernel/DTB 检查下载缓冲区与内存范围，并验证 kernel ext4 的单文件覆盖及未选内容保留。

出口：固件输入可复现，ext4 独立覆盖路线可用；真实板卡证据由开发者提供。能力不满足目标时先对齐方案。

## R2 · 制像、归档与主机 CLI

定义外部布局、启动描述和组件定位，按真实载荷及预留量确定默认几何。生成 kernel 分区与 rtfs 分区 Sparse，完成归档打包/解包、一键部署和各组件独立更新入口。

共用主机预检、只读目标探测、范围计划、正式确认、UUU 执行、固件 hash 门控及写后验证。布局更新必须同时提供受影响分区的新镜像。主机 `--dry-run` 不下载 loader、不写板。

出口：主机检查及 UUU dry-run 通过，开发者可审阅完整操作文档。验证 Sparse 有效块、文件覆盖与未选内容保留，不把主机测试当成实板验收。

## R3 · Tauri/React GUI

GUI 调用同一后端，提供输入选择、profile 编辑、实际分区与镜像信息、操作计划、确认、进度及错误结果。按屏幕中心约 1/4 面积设置初始窗口。

出口：GUI 与 CLI 生成相同目标和范围，错误与断连停止后续操作。

## R4 · 板卡验收与 BR 消费接入

由开发者以 03 BusyBox 载荷验证一键部署、boot0 冷启动、全部组件独立替换、指定范围擦除、固件免重复擦写及启动配置修改。验证布局变更必须伴随匹配镜像。

之后由 issue 01 接入真实 BR 系统，独立验收 systemd 冷启动。完整构建与硬件写操作交由开发者执行；全部判据通过后归档 issue。
