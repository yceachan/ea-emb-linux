## B 未对齐行为

| 用户意图或确认 | 实现／交接偏差 | 造成的影响 |
|---|---|---|
| profile 只描述分区布局 | schema 强制混入 firmware 和 boot；后端、制像、归档依赖同一对象 | 布局变更与固件、启动配置边界混淆 |
| 布局 profile 更新重建两个 ext4 | 旧设计只要求受影响分区的新镜像；后续只改文档，未实现新规则 | 无法保证两个旧文件系统同时不可达 |

## D 验证证明了什么

三组件构建、归档校验、26 项主机测试和 native ext4 检查曾通过。发布输入的八项 hash 与记录匹配，bundle 和解包清单各有 13 项通过。

这些结果证明部分构建与主机路径可运行，不证明完整产品可用。测试未覆盖上述角色互换、空盘探测与计划误报的触发条件。

| 未证明部分 | 证据边界 |
|---|---|
| GUI 完整交互 | 窗口出现和直接 Python RPC 不覆盖真实文件选择、确认与取消链路 |
| journal 专用读失败 | deinit-jsb-read 注入点实际落在 journal inode 读取，不能声称覆盖 JSB 数据读取失败 |
| 新需求 | 双 ext4 更新规则与 GUI 改版没有产品实现，也没有相应验证 |
| 实板交付 | 烧录、冷启动及组件保留内容没有本轮实板验收 |

固件短读传播与 RECOVER 清理问题此前已有修复。没有依据将其重新列为当前未修复缺陷，也不能用这些修复抵消其他失败。

## E 失败原因与经验

需求、实现事实、建议和验收证据被混写，导致旧代码结构反过来定义用户需求。应先明确对象职责，再评价实现是否满足职责；现有字段不能自动成为需求。

后续确认没有同步到实现和验证状态。确认新要求后，应撤销受影响部分的完成结论，而不是只修改文档。

审查把缺陷修复与新增能力混在一起。每个修复要求都应能追溯到原始需求、明确的用户确认或真实故障；无法追溯的方案不能塞入交接。

主机测试、固件构建、GUI 交互和实板启动有不同的证明范围。交付状态应由用户任务是否可完成决定，不能用测试数量或产物齐全替代。
